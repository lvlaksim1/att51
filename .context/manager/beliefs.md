## B3. Назначение и устройство — подтверждены как результаты статического исследования; не путать с испытанием
- Отчёт research/OPERATING_CYCLE.md связывает запуск attstart51.exe с Microsoft Word, запускающим шаблоном start51.dot и надстройкой Attestation51.dot. Программная логика распределена между VBA надстройки и шаблонов Word; постоянные данные и документы связаны с Access MDB, DOC/DOCX и XML.
- Отчёт указывает на 569 восстановленных модулей VBA главной надстройки. В этой генерации менеджера извлечение модулей **не повторялось**, поэтому численность и индивидуальные вызовы нужно независимо воспроизвести при последующем аудите, прежде чем считать полной картой кода.
- Выделены этапы: запуск → база рабочих мест → структура организации и РМ → факторы → создание протокола → ввод и расчёт → «Отправить в базу РМ» → отчёты и выгрузка.
- Важно: обычное сохранение Word и «Отправить в базу РМ» — разные операции по описанию исходных макросов. Требуется проследить фактические изменения MDB/DOC/XML на воспроизводимом примере.
- Источники: research/OPERATING_CYCLE.md и оригинальные extracted/app/start51.dot, Attestation51.dot, model/ARMv51.MDB, шаблоны протоколов; authority: repository-based static research, без проверки исполнения.

## B5. Границы доказательности
- Реальная работа Windows/Word и сетевых интеграций **не проверялась**. Полная корректность алгоритмов оценки каждого фактора и связность всех схем Access остаются открытыми вопросами.
- Программа может изменять структуру MDB при открытии (по отчёту о статическом исследовании); для любых опытов требуются копии и отдельное разрешение на запуск.
- В репозитории нет отдельного механизма запуска именно постоянного менеджера: обнаруженные GitHub Actions относятся к хранению и восстановлению файлов, а не к выполнению задач ИИ. Прямое обращение владельца через чат является допустимым способом вызова менеджера; открытая задача GitHub сама по себе не запускает его.
- Источники: research/OPERATING_CYCLE.md, список .github/workflows/ в main, .context/manager/PROTOCOL.md; authority: repository observation.

## B6. Цепочка XML для ФГИС ФСА — статически подтверждено
- Исследован именно оригинальный экспорт для ФГИС Росаккредитации. Двухэтапная цепочка: Word-протокол → внутренний XML по РМ → выбор через таблицу sout_factors основной MDB либо docs_list.xml сводных протоколов → сопоставления ATT_DEVICE/ATT_PERSON/FGIS_RA и DIC_ND из ресурсной MDB → построение ResearchObject через v52_exp_fgis_ra2025 → сохранение fsa_prot.xml и локальная проверка fileProtocolLoad_v4.xsd. Статический источник: research/FGIS_FSA_XML_PIPELINE.md, исходные VBA в extracted/app/Attestation51.dot. Фактический запуск и загрузка в ФСА не проверены.
- Выявлено статическое расхождение: DataStatusId и ProtocolStatusId при выбранных статусах записываются с текстовыми пояснениями, тогда как fileProtocolLoad_v4.xsd требует xs:int. Это повод для воспроизводимого теста, **не** доказательство неработоспособности реальной выгрузки.
- Важно хранить рабочие res_orgs.mdb, options.ini, fgis_ra.ini и каталог *_files наряду с основной MDB. Полные сведения в research/FGIS_FSA_XML_PIPELINE.md.
